## 1. 보고서 개요

### 1.1 목적

FinOps Data Platform은 금융 거래 데이터를 검증하고 MySQL에 적재한 뒤 API와 대시보드를 통해 조회하는 데이터 처리 시스템이다.

금융 거래 데이터는 중복 적재, 비정상 데이터, 처리 도중 중단 등의 문제가 발생하면 거래 건수와 집계 결과의 신뢰성이 저하될 수 있다.

따라서 단순히 정상적인 데이터 적재를 구현하는 것을 넘어 장애가 발생했을 때 데이터의 일관성이 유지되는지 검증하고, 장애 원인을 추적하고 복구할 수 있는 구조를 마련하는 것을 목표로 했다.

본 보고서는 V1~V3 개발 과정에서 수행한 장애 재현 및 복구 실험을 통합 정리한다.

### 1.2 검증 범위

- 데이터베이스 연결 실패 및 복구
- ETL 실행 실패와 오류 로그
- 트랜잭션 중간 실패 및 롤백
- 실패한 거래의 재처리
- 동일 데이터의 중복 적재 방지
- 잘못된 거래 데이터 검증 및 분리
- 배치 동시 실행 방지
- 데이터 품질 검사 실패
- 프로세스 강제 종료(SIGKILL)
- API 입력 오류 및 인증·인가 실패

실험 결과는 실제 수동 실행 결과, pytest 테스트, GitHub의 구현 코드 및 프로젝트 진행 기록을 근거로 정리했다.

실행하지 않은 실험이나 확인되지 않은 결과는 완료한 것으로 간주하지 않는다.

## 3. F-01, F-02 — 데이터베이스 연결 실패 및 복구

### 3.1 문제 정의

FastAPI는 MySQL 데이터베이스에 연결해 거래 및 계좌 정보를 조회한다.

MySQL이 중지되면 연결을 생성할 수 없어 정상적인 API 응답이 불가능하다.

이때 데이터베이스 연결 실패가 사용자에게 정상적인 응답으로 전달되거나 예외 처리가 제대로 이루어지지 않으면 장애 상황을 파악하기 어려워진다.

### 3.2 장애 재현 방법

Docker Compose에서 MySQL 컨테이너를 중지했다.

```bash
docker compose --env-file .env.docker stop db
```

이후 데이터베이스 연결을 확인하는 API를 호출했다.

```text
GET /health/db
```

### 3.3 관찰 결과

DB 연결 실패 상황에서 다음 응답이 반환됐다.

```json
{
  "detail": "Database unavailable"
}
```

HTTP 상태 코드: **503 Service Unavailable**

### 3.4 원인 및 해결

MySQL 컨테이너가 중지되면서 `mysql.connector`가 새로운 DB 연결을 생성할 수 없었다.

FastAPI에서는 데이터베이스 관련 예외를 처리해 HTTP 503을 반환하도록 구현했다.

```python
except mysql.connector.Error as e:
    logger.error(
        "Database health check failed: %s",
        e.__class__.__name__
    )

    raise HTTPException(
        status_code=503,
        detail="Database unavailable"
    )
```

오류 클래스명을 로그에 기록하여 장애 원인을 추적할 수 있도록 했다.

### 3.5 복구 검증

MySQL 컨테이너를 재시작했다.

```bash
docker compose --env-file .env.docker start db
```

DB가 정상화된 후 API를 다시 호출한 결과 HTTP 200 응답을 확인했다.

```json
{
  "database": "connected"
}
```

### 3.6 결과

- DB 연결 실패 감지 성공
- HTTP 503 반환 확인
- DB 재시작 후 HTTP 200 복구 확인
- 장애 원인 확인을 위한 로그 처리 구현

**한계:** 데이터베이스를 자동으로 재시작하거나 장애 발생 시 자동으로 알림을 보내는 기능은 구현하지 않았다.

## 4. F-03 — ETL 실행 중 DB 연결 오류

### 4.1 문제 정의

ETL 파이프라인을 자동으로 실행하는 경우, DB 연결에 실패해도 성공한 작업으로 기록되면 안 된다.

특히 cron과 같은 스케줄러는 프로그램의 종료 코드와 로그를 통해 실행 결과를 확인할 수 있어야 한다.

### 4.2 구현

`scripts/run_etl.py`에서 `subprocess.run()`을 사용해 ETL을 실행한다.

ETL의 표준 출력과 표준 오류를 수집하고 실행 결과를 로그에 기록하도록 구현했다.

```python
result = subprocess.run(
    [sys.executable, str(BASE_DIR / "src" / "load.py")],
    cwd=BASE_DIR,
    check=False,
    capture_output=True,
    text=True
)
```

실패하면 다음과 같이 오류를 기록한다.

```python
logging.error(
    "ETL failed (exit code: %s)",
    result.returncode
)
```

### 4.3 실험

V3 DAY 3에서 잘못된 DB 접속 설정을 사용해 연결 실패를 재현했다.

이후 `logs/etl.log`에 실패 로그가 생성되는지 확인하고, 접속 설정을 복구해 ETL을 재실행했다.

### 4.4 결과

- 데이터베이스 연결 실패 로그 확인
- ETL 오류 정보 기록 확인
- 연결 설정 정상화 후 ETL 실행 성공

### 4.5 한계

실패 시 종료 코드가 실제로 0이 아닌 값으로 반환되는지는 당시 명시적으로 검증하지 않았다.

또한 DB 연결을 생성하기 전에 오류가 발생하면 `pipeline_runs`에 실패 실행 기록이 만들어지지 않을 수 있다.

향후에는 실행 전 오류와 실행 도중 오류를 구분해 기록할 필요가 있다.

## 5. F-04 — 거래 적재 중 예외 발생과 트랜잭션 롤백

### 5.1 문제 정의

여러 거래를 DB에 적재하는 도중 오류가 발생하면 일부 거래만 저장될 수 있다.

이런 부분 적재는 거래 건수와 금액 집계에 오류를 발생시킬 수 있다.

따라서 적재 도중 실패하면 아직 확정되지 않은 변경 사항을 취소해야 한다.

### 5.2 해결 방법

MySQL 트랜잭션을 사용해 데이터 적재를 하나의 작업 단위로 처리했다.

정상 처리 시 `COMMIT`하고, 예외 발생 시 `ROLLBACK`하도록 구현했다.

### 5.3 장애 재현

`tests/test_pipeline_failure.py`에서 다음 순서로 실험했다.

1. 테스트 실행 이력 생성
2. 거래 1건 INSERT
3. `RuntimeError` 강제 발생
4. `conn.rollback()` 실행
5. 실행 상태를 `FAILED`로 변경
6. 별도 DB 연결에서 거래 및 실행 상태 조회

### 5.4 검증 결과

| 검증 항목 | 결과 |
|---|---|
| 강제 예외 발생 | 성공 |
| 미확정 거래 롤백 | 성공 |
| 테스트 거래 잔존 건수 | 0건 |
| Pipeline 실행 상태 | FAILED |
| 기존 테스트 결과 | 1 passed |

### 5.5 결론

Python의 예외 처리와 MySQL 트랜잭션을 이용해 적재 도중 실패했을 때 미확정 거래가 남지 않도록 처리했다.

실행 시작 이력은 먼저 확정하고, 실패 상태는 별도로 기록해 장애를 추적할 수 있도록 설계했다.

## 6. F-05 — 실패한 거래의 재처리

### 6.1 문제 정의

장애가 발생한 거래를 복구하기 위해서는 단순히 롤백하는 것뿐 아니라 동일한 데이터를 다시 처리할 수 있어야 한다.

재처리 과정에서 거래가 중복 저장되어서는 안 된다.

### 6.2 테스트 방법

`tests/test_pipeline_retry.py`에서 다음 과정을 검증했다.

1. 테스트 거래 생성
2. 거래 INSERT
3. 강제 예외 발생
4. ROLLBACK
5. 거래가 남아 있지 않은지 확인
6. 동일 거래 재실행
7. COMMIT
8. 다시 동일 거래 실행
9. 최종 거래 건수 확인

### 6.3 실제 결과

| 단계 | 거래 건수 |
|---|---:|
| 테스트 시작 | 0 |
| 롤백 후 | 0 |
| 재처리 및 COMMIT 후 | 1 |
| 동일 거래 재실행 후 | 1 |

재실행 시:

- 신규 적재: 0건
- 중복 처리: 1건

2026년 11월 21일 테스트 결과:

```text
1 passed
```

### 6.4 결론

실패한 거래를 다시 처리해도 정상적으로 적재할 수 있으며, 이미 저장된 거래는 중복으로 분류되어 추가 적재되지 않는 것을 확인했다.

이는 거래 테이블의 데이터 정합성을 유지하는 데 필요한 재처리 정책을 검증한 것이다.

다만 실행 이력 및 거부 거래 테이블까지 포함한 전체 시스템의 완전한 멱등성을 의미하지는 않는다.

## 7. F-06 — 동일 CSV 반복 적재

### 7.1 문제 정의

스케줄러의 재시도나 사용자의 재실행으로 동일한 CSV 파일이 여러 번 처리될 수 있다.

동일한 거래가 반복 저장되면 실제 거래 건수보다 DB에 저장된 거래 건수가 많아지는 문제가 발생한다.

### 7.2 해결 방법

`transaction_id`를 기본키로 사용했다.

MySQL의 `ON DUPLICATE KEY UPDATE`를 이용해 이미 존재하는 거래는 신규 INSERT로 처리하지 않도록 구현했다.

```sql
ON DUPLICATE KEY UPDATE
    transaction_id = transaction_id
```

### 7.3 실험 결과

기존에 적재한 10,000건의 거래 CSV를 다시 실행한 결과다.

| 구분 | 건수 |
|---|---:|
| 입력 거래 | 10,000 |
| 신규 적재 | 0 |
| 중복 거래 | 9,854 |
| 오류 거래 | 146 |

검증:

```text
0 + 9,854 + 146 = 10,000
```

### 7.4 결론

같은 거래 파일을 반복 실행해도 정상 거래 9,854건이 신규 거래로 중복 적재되지 않는 것을 확인했다.

금액이나 거래 날짜가 아닌 고유한 거래 식별자를 기준으로 중복 여부를 판단하도록 설계했다.

## 8. F-07 — 비정상 거래 데이터 검증 및 분리

### 8.1 문제 정의

실제 데이터 수집 과정에서는 필수 필드 누락, 잘못된 금액, 존재하지 않는 계좌 등의 문제가 발생할 수 있다.

이런 데이터를 검증하지 않고 적재하면 데이터의 신뢰성이 저하된다.

### 8.2 해결 방법

Python 검증 로직을 이용해 입력 데이터를 정상 거래와 오류 거래로 분리했다.

정상 거래는 `transactions`에 적재하고 오류 거래는 `rejected_transactions`에 저장하도록 구현했다.

오류 거래에는 다음 정보를 기록한다.

- 거래 식별자
- 원본 레코드(JSON)
- 오류 유형
- 오류 메시지
- 파이프라인 실행 식별자

### 8.3 검증 결과

| 구분 | 건수 | 비율 |
|---|---:|---:|
| 전체 입력 | 10,000 | 100% |
| 정상 거래 | 9,854 | 98.54% |
| 오류 거래 | 146 | 1.46% |

대표적인 오류 유형:

- `INVALID_AMOUNT`
- `UNKNOWN_ACCOUNT`
- `MISSING_FIELD`

### 8.4 결론

오류 데이터가 포함되어도 정상 거래와 오류 거래를 구분할 수 있었으며, 잘못된 데이터를 단순히 삭제하지 않고 추적 가능한 형태로 보관하도록 구현했다.

## 9. F-08 — 배치 동시 실행 방지

### 9.1 문제 정의

cron으로 배치를 정기 실행할 때 이전 실행이 끝나기 전에 다음 실행이 시작될 수 있다.

두 개 이상의 ETL 프로세스가 같은 데이터를 동시에 처리하면 데이터베이스 경합이나 실행 이력 혼란이 발생할 수 있다.

### 9.2 해결 방법

Linux의 `flock`을 이용해 동일 배치가 동시에 실행되지 않도록 했다.

### 9.3 검증 결과

V3 DAY 3에서 다음 내용을 검증했다.

- cron 1분 간격 실행
- ETL 실행 로그 생성
- flock을 이용한 동시 실행 차단
- 정상 ETL 실행 확인

프로젝트 진행 기록에는 동시 실행 방지 실험이 성공한 것으로 기록되어 있다.

### 9.4 한계

- 실제 매일 02:00 스케줄 실행은 아직 별도로 확인하지 않았다.
- cron과 flock 설정은 GitHub 저장소만 복제해도 자동으로 구성되는 형태가 아니다.
- WSL이 종료되어 있으면 해당 환경의 cron도 실행되지 않을 수 있다.
- 상세 실험 당시의 원본 터미널 로그는 본 보고서에 첨부되지 않았다.

## 10. F-09 — 데이터 품질 검사 실패

### 10.1 문제 정의

데이터 적재에 성공하더라도 저장된 데이터가 분석에 적합한 품질을 유지한다고 보장할 수 없다.

따라서 적재 이후에 별도의 품질 검사를 수행할 필요가 있다.

### 10.2 구현한 검사

- 비정상 금액
- NULL 값
- 중복 거래 식별자
- 존재하지 않는 계좌 참조
- 파이프라인 처리 건수 불일치
- 오류 유형별 발생 건수
- 배치 실행별 오류율

### 10.3 테스트 방법

`tests/test_quality.py`에서 세 가지 상황을 검증하도록 구현했다.

**정상 상황**

모든 검사 결과가 0이면 `PASS`를 반환한다.

**단일 오류 상황**

`pipeline_count_mismatch`가 1이면 `FAIL`을 반환한다.

**복합 오류 상황**

비정상 금액, NULL 값, FK 오류가 동시에 존재하는 검사 결과를 전달하면 `FAIL`을 반환한다.

### 10.4 결과

단위 테스트 3개가 통과한 것으로 이전 작업에서 확인했다.

또한 실제 데이터 품질 검사 실행 결과에서는 주요 무결성 검사가 모두 PASS로 나타났다.

기록된 배치별 오류율은 1.46%였다.

### 10.5 한계

- 세 가지 pytest 테스트는 검사 결과를 직접 입력하는 단위 테스트다.
- 실제 DB에 품질 불량 데이터를 삽입하는 통합 테스트까지 완료한 것은 아니다.
- 품질 검사 결과가 cron 배치의 성공·실패 상태에 자동으로 연동되지는 않았다.
- 오류율에 대한 별도의 FAIL 임계값은 아직 설정하지 않았다.

## 11. F-10 — SIGKILL에 의한 Python 프로세스 강제 종료

### 11.1 실험 목적

기존 롤백 테스트에서는 Python 코드에서 `RuntimeError`를 발생시킨 후 `conn.rollback()`을 호출했다.

하지만 실제 운영 환경에서는 프로그램이 갑자기 종료되어 Python의 예외 처리 코드가 실행되지 못할 수 있다.

따라서 프로세스를 강제로 종료했을 때 MySQL이 미확정 거래를 안전하게 처리하는지 확인했다.

### 11.2 테스트 환경

- DB: `finops_test_db`
- 계좌: 1건
- 최초 거래: 0건
- 최초 파이프라인 실행 이력: 17건
- 테스트 거래 금액: 50,000원
- 종료 방식: SIGKILL
- COMMIT: 실행하지 않음

### 11.3 장애 재현 과정

1. 테스트 DB 연결
2. 거래 1건 INSERT
3. COMMIT하지 않은 상태 유지
4. Python 프로세스에 SIGKILL 전송
5. 별도의 DB 연결 생성
6. 동일한 거래 식별자 조회

강제 종료에 사용한 핵심 코드:

```python
os.kill(os.getpid(), signal.SIGKILL)
```

### 11.4 실제 결과

| 항목 | 결과 |
|---|---|
| INSERT 실행 | 성공 |
| 명시적 COMMIT | 실행되지 않음 |
| SIGKILL | 실행 |
| 프로세스 종료 코드 | 137 |
| 종료 후 동일 거래 조회 | 0건 |

### 11.5 원인 분석

SIGKILL은 프로세스를 즉시 종료하므로 Python의 `except`와 `finally` 블록이 실행되지 않는다.

따라서 이번 실험에서는 Python 코드가 명시적으로 `rollback()`을 수행하지 않았다.

그러나 프로세스가 종료되면서 DB 연결이 끊겼고, MySQL은 연결 종료를 감지한 후 커밋되지 않은 트랜잭션을 롤백했다.

### 11.6 결론

명시적인 Python 롤백 코드가 실행되지 못하더라도 MySQL이 미커밋 거래를 롤백하는 것을 확인했다.

이는 트랜잭션의 원자성이 데이터 손상을 방지하는 데 중요한 역할을 한다는 것을 보여준다.

### 11.7 검증 범위와 한계

이번 실험은 **단일 INSERT에 대한 프로세스 강제 종료 실험**이다.

실제 ETL 전체를 강제 종료한 것은 아니므로 다음 사항까지 검증했다고 주장할 수는 없다.

- 전체 배치 강제 종료 후 복구
- 비정상 종료 시 RUNNING 이력 자동 정리
- 자동 재시도
- 복구 소요시간 측정
- 전체 거래 집계의 복구 전후 비교

## 13. 장애 대응 설계에서 확인한 한계

### 13.1 비정상 종료 후 RUNNING 상태

현재 `start_pipeline_run()`은 실행 시작 정보를 먼저 COMMIT한다.

이는 장애 발생 후 실행이 시작됐다는 기록을 보존할 수 있다는 장점이 있다.

그러나 프로세스가 강제로 종료되면 이후 실행 상태를 `FAILED`로 변경하는 코드가 실행되지 못할 수 있다.

그 결과 `pipeline_runs`에 `RUNNING` 상태가 남을 가능성이 있다.

현재 이 상태를 자동으로 탐지하거나 정리하는 기능은 구현하지 않았다.

### 13.2 연결 생성 전 장애 기록

`src/load.py`에서는 `get_connection()` 호출이 메인 `try` 블록보다 앞에 있다.

따라서 DB 연결 자체가 실패하면 해당 코드의 예외 처리 흐름을 거치지 않을 수 있다.

상위 실행 스크립트에는 실패 로그가 남을 수 있지만, 데이터베이스 실행 이력에는 실패 기록이 남지 않을 수 있다.

### 13.3 자동 재시도 부재

현재 시스템에는 실패한 배치를 운영자가 재실행할 수 있는 구조가 있지만, 실패를 탐지한 후 자동으로 재시도하는 기능은 구현하지 않았다.

### 13.4 복구시간 측정 부재

장애를 재현하고 복구에 성공했지만 복구 시작 시각부터 정상화까지 걸린 시간을 체계적으로 측정하지는 않았다.

따라서 RTO를 실제 측정했다고 주장할 수 없다.

## 14. 최종 검증 결과 및 기술적 성과

이번 프로젝트에서 확인한 주요 성과는 다음과 같다.

1. MySQL 트랜잭션을 이용해 적재 중 발생한 오류에 대한 롤백을 검증했다.
2. 실패한 거래를 재처리한 뒤에도 중복 거래가 생성되지 않음을 확인했다.
3. 10,000건의 입력 데이터를 대상으로 146건의 오류 거래를 분리했다.
4. 동일 CSV를 반복 실행했을 때 기존 정상 거래 9,854건이 중복 적재되지 않음을 확인했다.
5. DB 연결 실패에 대해 HTTP 503을 반환하고 복구 후 HTTP 200으로 정상화되는 것을 확인했다.
6. cron과 flock으로 배치 실행 자동화 및 동시 실행 방지 기능을 구성했다.
7. 데이터 품질 검사에서 정상·오류 상황을 구분하는 자동 테스트를 수행했다.
8. SIGKILL을 이용해 프로세스가 강제 종료되어도 미커밋 거래가 남지 않음을 확인했다.
9. API 입력 오류 및 인증·인가 실패에 대한 예외 처리를 자동 테스트로 검증했다.

단, 이러한 개별 검증 결과는 시스템 전체의 자동 장애 복구나 운영 환경에서의 고가용성을 증명하는 것은 아니다.

## 17. 최종 결론

FinOps Data Platform V1~V3 개발을 통해 금융 거래 데이터 처리에서 발생할 수 있는 중복 입력, 오류 레코드, 데이터베이스 연결 실패, 트랜잭션 중단 및 비정상적인 프로세스 종료 상황을 재현하고 검증했다.

특히 Python 예외 처리에 의한 명시적 롤백과 SIGKILL 상황에서 MySQL이 수행하는 미커밋 트랜잭션 롤백을 구분해 실험했다.

또한 실패 후 재처리와 거래 식별자 기반 중복 방지를 검증함으로써 반복 실행이 가능한 금융 데이터 파이프라인의 기본적인 안정성을 확인했다.

다만 자동 장애 복구, 전체 배치 강제 종료 후 실행 상태 복구, 복구시간 측정 등 운영 안정성을 위한 일부 기능은 미구현 상태다.

본 프로젝트의 주요 성과는 다양한 장애 상황에서 시스템의 동작을 실제 코드와 테스트로 검증하고, 그 한계까지 명확하게 기록했다는 데 있다.
